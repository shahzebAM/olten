# Document expiry reminders

The existing Prisma `Document` and `DocumentReminder` fields store this workflow. No schema change or new migration is required.

## Upload and reminders

1. Select documents or pictures in AI Docs. Upload starts immediately, with up to two files processed concurrently, an approximate time remaining for each active file, and a separate reading/saving phase.
2. Each upload goes to Google Drive. Gemini reads the source content and returns a validated expiry date and supporting text. Large native files share one Gemini upload for search indexing and expiry detection; PDF text checks run alongside network processing. Small files retain inline analysis. The date saved in the database is also the date returned to the frontend.
3. After upload, review one file at a time in selection order, with a file counter and read-only expiry/source text. Use the eye icon to compare it with the original. Choose days or calendar months and click Save Reminder for only that file, or Close Without Reminder to keep it stored without an active reminder. Either choice advances to the next file; the last choice closes the modal. A save failure keeps the current file and its settings visible for retry. Ambiguous dates, unreadable files, and analysis failures require reanalysis or a clearer source; they can also be skipped. A successful analysis with no expiry date creates no reminder.
4. If the calculated reminder date is today or earlier, the reminder is immediately due. Thus a document expiring tomorrow is due immediately with either a two-day or a two-month lead time. A zero-day lead becomes due on the expiry day.
5. Calendar months are subtracted with the day clamped to the destination month's final day (March 31 minus one month is February 28, or February 29 in a leap year).
6. Reminder timing remains editable; users cannot edit the expiry date. Successful reanalysis can update the date from the source and update its reminder. Saving unchanged settings preserves a fulfilled reminder. Deleting a document cascades to its reminders through the existing relation. The source preview offers Delete for the exact file, with confirmation; Drive failures keep the database document and report the error.
7. Replace Document is available for an indexed document with a detected date, including from a due reminder. Pick one file and confirm its name. The backend uploads to the current verified folder and analyzes the replacement while preserving the original. A reliable expiry and successful search indexing are required before the same database document ID swaps to the new Drive source. Existing days or calendar months are carried to the new expiry; disabled or pending reminder choices stay unscheduled. Replacement opens a one-file review showing the new date read-only, with Save Reminder or Close Without Reminder. The old source and index are cleaned up after the save; a cleanup failure reports a warning without undoing the saved replacement.

Notifications appear in the AI Docs reminder panel. The bell sits at the top right of the workspace header, and the panel stays closed until the user clicks it. Only due, unhandled reminders appear; future schedules have no Waiting card in the bell. New due reminders update its count without opening it. While this module is visible it refreshes every 30 seconds and on window focus; offline or failed requests back off, and the panel offers an explicit retry. When no enabled reminders are due, polling skips the Drive inventory scan. Email, SMS, operating-system push, and alerts while the application is closed are not configured.

Each reminder has an eye icon that opens its exact source document by document/Drive ID, so files with the same name cannot be mixed up. Negative countdowns are displayed as "Expired X days ago"; an expiry today is displayed as "Expires today". The server supplies calendar days remaining using the configured timezone.

Mark Handled removes the exact reminder card and document's blinking indicator immediately after a successful save. Its detected expiry and document status remain visible. The request pins the expected expiry cycle and Drive source, so a late click for an old source cannot dismiss the replacement's reminder.

The backend checks expiry statuses at startup and every minute. Notification reads calculate due status directly, so a custom reminder does not depend on waiting for the cron job. New frontend uploads store an internal pending-setup status until review is saved; cron and reanalysis preserve it and cannot create a default reminder before confirmation. Close Without Reminder deletes that file's reminder and legacy expiry notifications, and stores an internal disabled marker in the existing document status field. API responses return `reminder`, `reminderValue`, `reminderUnit`, and `reminderDays` as null; cron and reanalysis preserve this choice. Disabled files receive no alerts, including on the expiry day, and show no expiry alarm badge, countdown, or directory alert dot. Their detected expiry date and source evidence remain visible. Saving a new reminder explicitly enables it again. Legacy dated documents without a chosen schedule receive one default reminder; explicitly disabled files never receive it. A fulfilled user reminder suppresses default reminders.

PDF and supported raster-image previews load original bytes from a company-scoped authenticated API route. PDF.js renders one page at a time with page and zoom controls. Known PDFs start with a 256 KiB range and additional ranges needed for that page, while PDF engine and worker startup overlap the network request. This avoids waiting for an entire large PDF before rendering; the complete original is fetched only when Open PDF is clicked. Files whose server ignores ranges still work with a full-download fallback. Images and unknown MIME types keep a 1 MiB initial request; raster previews download the complete image. Each media request validates fresh file metadata and its parent ancestry to the selected company folder, avoiding a whole-directory scan without retaining server authorization decisions. MIME, signature, range, size, and version checks reject mismatched content; supported sources are limited to 100 MiB. PDF evaluation and XFA are disabled, and the renderer exposes no document scripting or embedded HTML. Its worker, fonts, CMaps, and WASM are served from the frontend origin.

Pointer, keyboard focus, or source-eye intent can prepare one PDF's first page before selection. Hover waits 150 ms and leaving early cancels it; the reader is shared with the actual viewer. Directory rendering never downloads all files. Speculation is disabled for data-saver and slow 2G connections, and aborts a large full-file response when a server ignores ranges. Actual viewing still supports the complete-download fallback. Workspace changes, logout, and exact-source deletion or replacement cancel speculative work and discard private readers.

Inline and modal viewers share fetched pages for the same company, signed session, source ID, and source version. Up to three unused readers representing at most 64 MiB of source files can remain for 60 seconds when modification metadata is available, or one second otherwise. Workspace/session changes and exact-file deletion discard readers, abort requests, and revoke image/download Blob URLs. Failed loads are not cached, and a stalled media request offers Retry after 30 seconds without incoming data. Other formats offer Open in Drive. Gemini citations are rendered as links only when they identify a current file through a valid HTTPS Google Drive/Docs URL. Previewing, paging, and editing reminders make no Gemini generation calls.

## Configuration

- Existing `GEMINI_API_KEY` and Google Drive OAuth/folder variables must be configured.
- `GEMINI_EXPIRY_MODEL` optionally selects the expiry model. It falls back to `GEMINI_MODEL`, then `gemini-3.6-flash`.
- Search accepts the two frontend models, `GEMINI_MODEL`, and optional comma-separated `GEMINI_SEARCH_MODELS`. Other requested models are rejected before a generation call, so a client cannot select an arbitrary costly model.
- Configure signed API sessions and allowed frontend origins as described in [Document API sessions](../auth/README.md). Set a shared `SESSION_SECRET` of at least 32 bytes, deploy backend and frontend together, and sign in again after deployment. No schema migration is needed.
- `DOCUMENT_EXPIRY_TIMEZONE` optionally selects an IANA timezone; the default is `Asia/Manila`. Expiry and trigger dates are calendar dates stored at UTC midnight, and due checks use this configured timezone.
- The PDF text reader requires Node.js 20.16 or newer (or 22.3 or newer on the Node 22 line).
- Install dependencies in both backend and frontend, then deploy or restart both after updating. The frontend build includes the PDF.js worker and its `pdfjs/` decoding assets; publish the complete build directory.

Expiry detection supports PDF, DOCX, readable UTF-8 text, JPG, PNG, WebP, HEIC, and HEIF. DOCX extraction includes text, tables, headers, footers, and supported embedded images. Other formats, linked or unreadable images, and unclear scans need PDF export or a clearer source. Analysis supports files up to 50 MB; large PDFs/images reuse their indexed Gemini file during upload, falling back to a temporary file if indexing fails. Reanalysis uses temporary files when needed. DOCX extracted content/image payloads have smaller limits.

The current schema stores one expiry per document. Detection targets the primary document's expiry, including labels such as "Validity of License". Expiries of staff IDs, supporting attachments, and unrelated documents must not replace the primary license/permit expiry. Review the date and its quoted evidence against the source; unclear scans or ambiguous dates cannot activate a reminder until reanalysis obtains a reliable date.

Reanalysis downloads the permanent Google Drive copy because Gemini file references expire after 48 hours. Reanalysis and remote deletion verify the exact source in the current company's Drive directory; previews verify fresh metadata and parent ancestry to that company folder. Sources moved out, trashed, or missing cannot be read or deleted through old indexes; their saved records remain available for recovery. Notifications also exclude these missing sources. Failed reanalysis preserves the current date and schedule. A reminder confirmed or disabled while pending-upload analysis is working takes priority over the older analysis result. Search indexing failures do not discard a successfully stored document and expiry reminder; the upload review reports the indexing warning separately. DOCX search indexing includes readable text; expiry analysis also reads supported embedded scans.

AI search uses only indexed documents whose exact Drive IDs still exist in the current company directory. An empty directory returns an empty answer without consulting Gemini or old cached context. Cache reuse requires the current source set to match, and a source change during analysis requires a fresh search. Deleted files and changed directory contents clear previous displayed answers, including responses still in flight. A Drive failure is reported instead of searching stale sources.

## Gemini token use

Expiry extraction and search now use bounded responses and model-aware thinking settings. Gemini 3/3.0/3.5/3.6 Flash variants use minimal thinking; other Gemini 3 Flash variants and Pro use low thinking. Gemini 2.5 Flash/Lite disable optional thinking. Unknown model families keep their own thinking defaults. The default output allowance is 2048 tokens, or 4096 for Pro; this includes thinking as well as the visible answer. Optional `GEMINI_EXPIRY_MAX_OUTPUT_TOKENS` and `GEMINI_SEARCH_MAX_OUTPUT_TOKENS` accept whole numbers from 1024 to 16384. Invalid overrides use the defaults. A response stopped by its token limit is rejected rather than saving an incomplete date or answer.

Original PDFs remain available to Gemini, including scans. Their first reading uses medium media resolution; photographs and independent verification retain high resolution for legibility. Readable text and Word content can confirm an exact quoted date locally. A clear photo of a primary license validity label can use one reading. Unclear dates, competing primary labels, generic staff-license dates, and uncorroborated scanned PDFs retain independent verification. A confident complete reading with no expiry does not require a duplicate call; missing extracted PDF text alone never means no expiry.

During upload, byte-identical documents with the same normalized MIME type and expiry model share concurrent analysis and reuse successful results for 10 minutes, bounded to 128 entries. The source uploads and document records stay separate. Errors are never cached, and explicit Re-analyze always performs fresh analysis. Saving or skipping a reminder and refreshing notifications use no Gemini generation calls.

Simple complete file-list questions are answered from the current Drive directory without Gemini, including files still waiting for search indexing. Content questions continue to use Gemini. Exact repeated questions reuse a recent answer for five minutes, bounded to 128 answers, and simultaneous identical questions share a generation request. Reuse is scoped by company, model, source fingerprint, and company calendar day. Every caller verifies the current Drive sources before returning an answer. The fingerprint includes file modification time, size, and checksum when available, so changed or deleted sources invalidate reuse. Reused answers and inventory responses record zero new generation tokens in search history.

Context setup is shared between concurrent requests, and up to 64 successful context references remain reusable across model switches for 55 minutes. A context-cache failure is remembered for five minutes instead of repeatedly attempting an unsupported cache; ordinary search still works. These process-local caches clear on backend restart and do not require schema changes. Savings depend on file type, ambiguous evidence, repeated uploads/questions, and Google's context-cache eligibility; this does not promise a fixed reduction in billed tokens.

Concurrent directory reads for one company share a pending Drive scan and receive isolated copies. Completed reads have no lasting directory cache, and mutations invalidate older scans before refresh. Concurrent uploads also share a pending company-folder lookup to avoid creating duplicate roots. These request savings add no Gemini generation calls or schema fields.

The media/thinking settings follow Google's [media-resolution](https://ai.google.dev/gemini-api/docs/generate-content/media-resolution), [document-processing](https://ai.google.dev/gemini-api/docs/generate-content/document-processing), and [thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking) guidance.

## API compatibility

`POST /api/docs/upload` accepts the existing multipart fields plus `reminderDays` or the pair `reminderValue`/`reminderUnit` (`days` or `months`). The frontend sends `reminderSetup=after-upload` to defer scheduling until review is saved, and responses include `reminderSetupPending`. Older callers without this flag retain automatic scheduling with a default 30-day lead. Lead times must be whole numbers in 0–36500 days or 0–1200 months.

`POST /api/docs/save-reminders` keeps the existing `{ reminders: [...] }` payload and accepts the same lead-time fields. Each row needs a company-owned document ID with a reliable stored expiry. Omit `expiryDate`; the server uses its stored date. Legacy callers may supply the identical date, but a different date is rejected. Numeric database IDs and stored Google Drive IDs are accepted. Invalid rows reject the batch and all changes are rolled back together.

`PATCH /api/docs/:id/manual-expiry` is retained only for compatible reminder timing updates against the same stored expiry; changing the expiry is rejected. Reanalysis and reminder updates resolve both database and Drive IDs within `x-company`. Directory responses preserve Google Drive file IDs and add `documentId`, expiry metadata, and the current reminder.

`DELETE /api/docs/:id` requires `x-company` and verifies the exact company-owned database or Drive ID. Folder deletion also cleans indexed descendants and their reminders. Select only the outermost folders/items when deleting a batch.

`DELETE /companies/:name` still requires a Super Admin session. It immediately looks up existing folders with the exact company name directly under `GOOGLE_DRIVE_FOLDER_ID`, verifies their current ownership scope, and permanently deletes those roots before committing company deletion. The folder operation removes its owned descendants through Google's [folder deletion API](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/delete), without scanning or generating AI content for each document. Missing roots are safe to retry; lookup, verification, and Drive failures keep the database company available for retry. A database failure after Drive removal also reports a retryable error. Active uploads/replacements finish first, and new storage creation is blocked during deletion. Late reads and multipart uploads cannot recreate a deleted folder; a newly created company with a different database ID can resume normal storage access. Company document records, their cascading reminders/notifications, and document search history are removed in the same database transaction; Gemini file indexes are cleaned up afterward without delaying success. Unrelated company data tables are unchanged. The gateway waits for completion, prevents duplicate clicks, and displays failures instead of reporting early success. No schema migration is needed.

`DELETE /api/docs/:id/reminder` persists Close Without Reminder for one file, preserves its source and detected expiry, and returns null reminder timing. `GET /api/docs/:id/content?source=document|drive` streams a current company-owned source, with private/no-store and nosniff headers. It supports a single byte `Range` and optional `If-Range`, returning accurate 200/206/416 responses, file length, and a version ETag when available. CORS permits Range/If-Range and exposes the media response headers to the configured frontend origins. All document routes require a signed bearer session with access to AI Docs and the selected existing company; the authenticated username replaces client-supplied identity headers.

`POST /api/docs/:id/replace` accepts one multipart `file` up to 50 MiB and optional `expectedDriveFileId`. It keeps the existing document ID and verified parent folder. A changed source, missing reliable expiry, indexing failure, or database conflict preserves the previous record and schedule; staged remote files are cleaned up. Metadata and atomic database checks reject stale edits while allowing routine cron timestamps to change during analysis. Responses include the new `driveFileId`, `sourceUrl`, source version metadata, expiry, reminder state, and optional `cleanupWarning`.

Notification status updates require `x-company` and accept `PENDING`, `PROCESSING`, or `FULFILLED`. They optionally accept `expectedExpiryDate` and `expectedDriveFileId`, rejecting an older expiry/source cycle with 409. Older callers remain compatible. Reminder responses include `reminderValue`, `reminderUnit`, `isTriggered`, `daysRemaining`, and exact `documentId`/`driveFileId`/`sourceUrl` fields alongside the existing fields.

Regression checks: `npm test -- --runInBand --testPathPatterns=documentation` and `npm run build` in the backend; `npm run build` in the frontend. Tests mock Gemini/Drive/database calls and do not exercise live credentials or upload real documents.
